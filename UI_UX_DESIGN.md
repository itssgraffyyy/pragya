# PRAGYA product design overhaul

## Baseline audit — 19 October 2026

Starting branch main, commit 5f2da00. Original user-owned diagnostics remain uncommitted and outside staging. The five existing modules, canonical engine/scorer, role checks and version-4 IndexedDB remain authoritative.

The initial UI uses independent homepage cards, per-screen Home buttons, basic Tailwind panels and a fixed 380px console form column. Three.js uses one R3F canvas, randomly scattered box buildings, cone trees, a ground plane and generalized contact silhouettes. There is one simulation-clock driver; cosmetic lights currently use render elapsed time. Graphics presets exist, but shadows are unconditionally enabled by the canvas. Existing verified checkpoint is 278 unit/component tests and 26 browser journeys; this assignment reruns that baseline.

## Original visual language

Graphite surfaces, warm off-white type, subdued teal actions and restrained amber/error signals. System fonts remain local and require no download. Tabular numerals identify measurements. Persistent grouped navigation maps to existing routes and permissions; there are no duplicate AssessGuard/EvidenceMind/CurriculumForge screens. The training viewport receives the largest workspace area, with independently scrolling decisions. Instruction and assessment screens use the same typography, table, form, focus, loading and status rules.

The supplied Arma Reforger, Ready or Not and DCS references inform environmental coherence, restrained hierarchy and precise instrumentation only. No game assets, layouts, textures, logos or tactical controls are copied.

## Preservation boundaries

No canonical trajectories, timestamps, sensor/evidence contracts, scoring rubrics, answer keys, assessment histories or storage migrations are changed for visual convenience. Navigation hiding supplements existing service permissions. Overview values must come from authorized real records; missing history is an empty state. Cosmetic motion must sample simulation time so pause freezes it. Quality presets may simplify decorative scenery and shadow cost, never assessment availability or visual identity.

## Milestone sequence

A: shared shell/tokens/navigation. B: contextual dashboard. C: urban/rural world and atmosphere. D: contact models/camera/presets. E: viewport-first console. F: assessment/learning hierarchy. G: institutional workflows. H: screenshot inspection, full regression, offline/accessibility/responsive checks, measured performance and documentation.

Validation, screenshots, commit IDs, remaining issues and performance observations are recorded in VISUAL_QA_REPORT.md as checks complete. Rendering budgets and original asset provenance are recorded in VISUAL_RENDERING.md.

## Assessment and learning hierarchy

The console uses explicit header/guidance/viewport/decision grid areas. Its observation, classification/confidence and evidence/response steps retain all original controls and instrumentation. Guided cues stay visible rather than moving behind disclosure. AAR displays the recorded rubric and category meters first, then AssessGuard eligibility and EvidenceMind's six separate judgment dimensions. Source references expand through native keyboard-accessible details. Confidence calibration remains a separate metric; no new composite is calculated.

WorkflowSteps, WorkspaceIntro and MetricCard provide shared presentation primitives. CurriculumForge and scenario quality use numbered guides, labeled fields, severity findings and a distinct coverage section. Skill DNA retains compatible cohorts and its actual score chart/table; Adaptive Training explains the baseline/practice/evaluation/follow-up sequence. Progress uses a real comparable-measurements table with source-session disclosure. These components consume existing services rather than duplicating their decisions or inventing sample progress.
